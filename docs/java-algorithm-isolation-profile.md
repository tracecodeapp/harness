# Java Algorithm Isolation Profile

The browser Java Judge has two correctness-batch tiers. Both tiers compile one
prepared artifact, run every correctness case, and preserve the existing policy
that only the selected case is traced. They differ only in the inner TraceJVM
boundary used between correctness cases:

| Tier | Per-case boundary |
| --- | --- |
| `algorithm-fast` | A fresh application class loader inside one retained TraceJVM process |
| `compatibility` | A fresh TraceJVM process |

The outer Judge and TraceKernel lifecycle does not change. Every case still
receives a fresh TraceKernel execution scope, and the Judge's algorithm syscall
policy remains the authority for files, processes, and network access. The
retained JVM is a performance boundary inside that policy, not a replacement
for it.

## Artifact-derived admission

The Java runtime derives the tier during trusted preparation from the exact
class-file bytes emitted by the compiler. A request cannot select
`algorithm-fast`, and a snapshot's stored profile is informational only.
Restored snapshots always select `compatibility`: their class bytes and entry
metadata are caller-controlled, and the current format has no independently
trusted provenance binding. Restore still scans every class byte so diagnostics
remain useful, but it cannot re-enter the fast tier. A future fast restore must
recompile through trusted preparation or authenticate the artifact against
state held outside the snapshot.

Admission scans learner class files and fails closed to `compatibility` when a
class file or reference descriptor cannot be parsed. The classifier recognizes
JVM constant-pool field and method references, the object types named by their
descriptors, and native declarations. Descriptor scanning is important for
capabilities such as `new Scanner(System.in)`, where the forbidden input stream
can otherwise appear only as a field or constructor type. It rejects ambient
capabilities whose state is not owned by a fresh application class loader,
including:

- files, channels, filename-based formatters/archives, processes, native
  loading/foreign-memory APIs, and network access;
- environment and system-property access;
- threads, cleaners, executors, parallel streams, and other concurrent
  execution;
- reflection, class loading, method handles, modules/module discovery, scoped
  values, and service loading;
- process-global logging, preferences, locale/time-zone mutation, and similar
  defaults;
- VM-global tables such as `String.intern`, which survive application class
  loader replacement;
- nondeterministic clocks and random-number generators, including the modern
  `java.util.random` family, system-backed `Clock` factories, and ambiguous
  current-time builders such as `Calendar.Builder`.

The one narrow `java.io` exception is output through the execution-scoped
`System.out` and `System.err` `PrintStream`s. Only output methods such as
`print`, `println`, `printf`, and `write` remain eligible. Constructors,
closing directly, through `AutoCloseable`, or through another JDK resource
owner, inspecting the stream, input streams, readers, files, serialization,
and every other `java.io` owner select `compatibility`.

Ordinary algorithm imports are not an opt-in capability. Collections, deques,
maps, math, text, and time value types continue to compile normally and remain
eligible when the emitted bytecode references only algorithm-scoped APIs.
Unsupported or ambiguous libraries do not fail compilation; they select the
compatibility tier.

During trusted preparation, only the exact export-shell identities generated by
the active Java worker, including their nested classes, are excluded. Each
preparation receives an unpredictable 128-bit shell identity rather than one
derived from learner-controlled source, so a learner cannot predeclare an
excluded `$`-nested lookalike. A class that merely resembles an `Exports...`
class is scanned. Restore excludes no class because all restored identities are
caller-controlled. Learner classes, including nested and synthetic classes,
are scanned. Java class files encode
strings as modified UTF-8, while the small browser-side parser accepts the
ordinary UTF-8 subset. A constant outside that subset is therefore treated as
unverifiable and safely falls back to `compatibility`.

## Per-case isolation and recovery

On the fast tier, each `process.run` creates a fresh application class loader.
Learner statics and class initialization therefore start clean. TraceJVM also
restores the execution scope it owns, including system properties, standard
streams, locale/time-zone defaults, current-thread metadata, and thread locals.
Any runtime isolation taint or retirement recommendation drops the retained
process before the next case. A clean process is also retired after at most 64
executions, so a larger batch receives another clean retained process rather
than extending the lease without bound.

The retained process host resolves the current outer TraceKernel request on
every syscall dispatch. Consecutive single-case trace requests can therefore
reuse one clean inner JVM without retaining the released channel client from
the prior request. If no current channel exists, the host fails closed with a
broken-pipe error instead of dispatching through stale authority.

The Judge keeps the per-case wall-clock budget. A timeout disposes the inner JVM
and the next case starts in a new process. Learner exceptions, incorrect
outputs, trace limits, and timeouts do not skip later correctness cases.
Compatibility artifacts start with that hard process boundary on every case.

## Benchmarking

The benchmark exercises `createBrowserJudgeHost` and the public Judge API in a
real browser. It compares bytecode-equivalent 100-case workloads whose only
material difference is an unreachable ambient system-property reference that
forces the compatibility tier:

```sh
TRACECODE_TRACEJVM_ROOT=/path/to/pinned-tracejvm-layout \
TRACECODE_JAVA_BENCHMARK_CASES=100 \
TRACECODE_JAVA_BENCHMARK_ROUNDS=3 \
node --import tsx scripts/benchmark-browser-java-algorithm-isolation.ts
```

This measures the learner-visible compile-and-correctness boundary, including
runtime preparation and completion of all cases. It does not measure a local
runner or call the prepared provider directly.

On the development Mac used for the final branch, three alternating 10-case
rounds produced a 1,528 ms fast-tier median and a 2,865 ms compatibility-tier
median. Three alternating 100-case rounds produced a 2,834 ms fast-tier median
and a 17,576 ms compatibility-tier median. Both tiers passed every case. The
100-case result is a 6.20x boundary improvement, not a cross-machine or
competitor claim; publishable numbers should be rerun on the named release
artifact and target hardware.

The browser regression suite also executes adversarial state probes. Learner
statics are reset by the fresh application class loader. Programs referencing
system properties, background threads, modules, class loaders, or files are
classified into the compatibility tier; two consecutive cases verify that none
of that state crosses the fresh-process boundary. Timeout, abort, disposal, and
ordinary learner-exception recovery remain covered independently. Additional
probes cover array-clone owners, the 64-execution lease boundary, and snapshots
that forge both entry identities and stored profile metadata around ambient
bytecode. Real browser probes also cover `String.intern` non-leakage,
unpredictable generated-shell identities, `$`-shaped learner lookalikes, and
two sequential single-case trace requests through distinct outer kernel
channels.

A still faster design could invoke Java once for the whole batch. Harness does
not use that shortcut: without engine-owned instruction budgets or safe
per-invocation cancellation, one infinite learner case could prevent recovery
and poison every later case. A single-invocation tier requires a corresponding
TraceJVM engine contract, not a weaker Judge timeout.
